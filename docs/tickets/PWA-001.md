# PWA-001 — Installer Derby Names comme Progressive Web App

## Contexte

Derby Names est une application publique consultée en mobilité pendant les événements de roller derby. L'expérience actuelle dépend entièrement du réseau et n'expose pas les métadonnées nécessaires pour être installée comme application depuis un navigateur compatible.

## Problème

Les utilisateurs ne peuvent pas ajouter Derby Names à leur écran d'accueil avec une identité applicative complète, et une perte de connexion empêche l'accès minimal à l'application déjà visitée.

## Périmètre

Inclusions :

- Ajouter un manifeste web applicatif servi depuis `public/manifest.webmanifest`.
- Fournir des icônes installables 192×192 et 512×512 à partir de l'identité visuelle existante.
- Déclarer les liens et métadonnées PWA dans le document HTML.
- Enregistrer un service worker côté client.
- Mettre en cache le shell applicatif et fournir un fallback pour la navigation hors ligne.
- Couvrir les métadonnées PWA par un scénario Gherkin et un test E2E.

Exclusions :

- Pas de stratégie offline complète pour les données dynamiques des API.
- Pas de notification push ni de synchronisation en arrière-plan.
- Pas d'ajout de dépendance PWA externe.

## Solution retenue

- Utiliser les fichiers statiques SolidStart du dossier `public` pour exposer le manifeste, le service worker et les icônes.
- Enregistrer `/sw.js` uniquement dans le navigateur lorsque `serviceWorker` est disponible.
- Mettre en cache uniquement les ressources GET same-origin hors `/api/` afin d'éviter d'exposer ou figer des données dynamiques.
- Servir la page d'accueil en fallback de navigation lorsque l'utilisateur est hors ligne après une première visite.

## Critères d'acceptation

1. Le document HTML expose `link[rel="manifest"]` vers `/manifest.webmanifest`.
2. Le manifeste déclare `name`, `short_name`, `start_url`, `scope`, `display: standalone`, `theme_color`, `background_color` et des icônes PNG 192×192 et 512×512.
3. Le client enregistre un service worker `/sw.js` sans bloquer le rendu si l'API n'est pas disponible.
4. Le service worker met en cache le shell applicatif et ignore les routes `/api/`.
5. Une navigation hors ligne peut retomber sur la page d'accueil mise en cache après une première visite.
6. `pnpm run typecheck` et le test E2E PWA passent.

## Scénarios Gherkin couverts

```gherkin
Scénario: L'application expose les prérequis d'installation PWA
  Étant donné que la page d'accueil est servie
  Quand le harnais inspecte les métadonnées PWA
  Alors un manifeste web est déclaré
  Et le manifeste permet un affichage standalone
  Et les icônes installables 192 et 512 pixels sont disponibles
  Et un service worker est servi
```

## Sécurité & accessibilité

- Le service worker ignore les requêtes non-GET, cross-origin et `/api/` pour limiter le risque de cache de données sensibles ou personnalisées.
- Aucune donnée utilisateur ni secret n'est ajoutée aux fichiers statiques.
- Les métadonnées conservent le thème et les comportements mobile existants sans modifier la navigation clavier ou le contenu sémantique.

## Risques & rollback

- Risque : une ressource statique obsolète reste en cache jusqu'au changement de version du service worker.
  Mitigation : versionner `CACHE_VERSION` à chaque évolution majeure de la stratégie de cache.
- Rollback : supprimer le lien manifest, l'enregistrement client et les fichiers `manifest.webmanifest`/`sw.js`/icônes PWA.
