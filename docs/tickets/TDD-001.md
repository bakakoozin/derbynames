# TDD-001 — Augmenter la couverture des tests unitaires

## Contexte

Le projet Derby Names possède déjà deux fichiers de tests unitaires (`src/utils/constants.test.ts`
et `src/utils/pending-club.test.ts`) mais la majorité de la logique métier applicative
(utils non couverts, routes API, contrôleur de toasts) reste non testée. La roadmap qualité
rattachée au runbook (`docs/release-runbook.md`) prévoit une exécution `pnpm test:unit` lors
du preflight code, ce qui n'a de valeur que si la suite est représentative.

L'objectif de ce ticket est d'étoffer la couverture sur les modules métier critiques en
restant sur l'harnais natif `node:test` (cohérent avec l'existant) et en mockant la base via
le `Mock` de `node:test`.

## Périmètre

Inclusions (modules à tester) :

- `src/utils/feature-flags.ts`
- `src/utils/pending-club.ts` (compléter : `makeUserProposedClubId`)
- `src/utils/users.ts` (`ensureUserIdByEmail`)
- `src/utils/premium-access.ts` (`derbynameHasPremiumBadgeAccess`)
- `src/ui/Toast/Toast.ctrl.ts`
- `src/routes/api/feature-flags.ts`
- `src/routes/api/check/[derbyname].ts`
- `src/routes/api/badge/[derbyname].ts`
- `src/routes/api/clubs.ts`
- `src/routes/api/rename-history.ts`
- `src/routes/api/validate/[token].ts`
- `src/routes/api/derbynames.ts`
- `src/routes/api/rpc.ts`
- `src/routes/api/premium/club-access.ts`
- `src/routes/api/premium/roster.ts`

Exclusions :

- Composants Solid (couverts par les tests E2E Playwright).
- Scripts `scripts/*` (exécutés via leur propre entrypoint).
- Aucun changement de code applicatif.

## Approche

- Réutiliser `node:test` + `node:assert/strict`, déjà présents dans le projet.
- Utiliser `mock` de `node:test` pour substituer `~/db` (et `~/utils/users` quand
  `ensureUserIdByEmail` est testé en interne).
- Conserver le style `test("…", () => { … assert… })`.
- Pas d'ajout de dépendance.

## Critères d'acceptation

1. `pnpm test:unit` exécute l'ensemble des nouveaux fichiers `*.test.ts`sans erreur
   et tous les tests passent.
2. Aucun test n'est `todo` ou `skip`.
3. `pnpm run typecheck` reste vert.
4. Les scénarios Gherkin existants (`specs/features/quality-harness.feature`) restent valides
   (aucune rupture).
5. Les branches métier suivantes sont couvertes (cas nominal et au moins un cas d'erreur) :
   - `feature-flags` : valeurs `1/true/yes/on`, casse, espaces, `undefined`.
   - `pending-club` : `makeUserProposedClubId` gère les accents, les caractères non-alphanum,
     le nom vide, et préfixe `u-`.
   - `users.ensureUserIdByEmail` : utilisateur existant / création / échec de relecture.
   - `premium-access.derbynameHasPremiumBadgeAccess` : derbyname non confirmé, club absent,
     pas de membership, membership illimitée, membership expirée.
   - `Toast.ctrl` : `addToast` (type par défaut, closable, auto-remove), `removeToast`,
     `clearAll`, helpers `success/error/warning/info`.
   - `api/feature-flags` : renvoie l'objet JSON.
   - `api/check/[derbyname]` : derbyname vide, type invalide, avec/sans résultat.
   - `api/badge/[derbyname]` : derbyname vide, flag premium désactivé, accès refusé,
     accès autorisé (avec génération SVG sécurisée).
   - `api/clubs` : tri avec `autre` en tête, échappement LIKE, fallback en cas d'erreur.
   - `api/rename-history` : POST valide / email invalide / pas de derbyname confirmé,
     GET token manquant / expiré / valide.
   - `api/validate/[token]` : token manquant, introuvable, expiré, payload invalide,
     derbyname introuvable, succès complet avec insertion club et historique.
   - `api/derbynames` POST : email invalide, regex XSS, numRoster > 4, nom du club < 2,
     derbyname déjà pris, replacement, club-only, création.
   - `api/rpc` : JSON invalide, méthode manquante, méthodes inconnues, dispatches
     nominaux.
   - `api/premium/club-access` : flag désactivé, données invalides, succès.
   - `api/premium/roster` : flag désactivé, clubId manquant, succès.

## Risques & mitigations

- **Couplage fort à `~/db` dans les routes API** : atténué par le mock de `getDb`.
- **Modules qui appellent `process.env` ou `fetch`** : mockés via `mock.method`/`mock.fn`.
- **Mocks qui "collent" en mémoire** : utilisation de `mock.reset()`/`mock.restoreAll()`
  dans `afterEach` pour isoler les tests.

## Livraisons

- Nouveaux fichiers `*.test.ts` à côté des modules testés.
- Mise à jour de `docs/tickets/TDD-001.md` (ticket) le cas échéant.
- Commit unique : `test: add unit coverage for utils, toasts and API routes`.
